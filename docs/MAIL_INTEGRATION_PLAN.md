# 邮箱接入与初赛收尾计划

## 承诺维护任务 — 当前派单基准

2026-10-04 用户确认：先解决“承诺与变更散落在消息中，手动维护费力”。任务按下列依赖执行，每项由 MiniMax 可见内环实现，Codex 外环独立复验；接入与官方能力限制先核实。

| 任务 | 开发范围 | 独立验收 |
| --- | --- | --- |
| COMMITMENT-001 | 梳理既有来源授权/云分析同意及安全存储缺口，接通一个来源的真实自动发现 | 默认不读、同意后自动发现；拒绝/停用/重启不继续；运行时新输入走真实模型并读回，不以预设回复替代 |
| COMMITMENT-002 | 维护同一事项的责任、期限、要求与状态；来源证据和变更前后可追溯 | “交稿→改期并补要求→取消”仍是同一事项；不同人/不同交付物不误合并；重复和乱序消息不倒退状态；矛盾信息待核实，取消不等于完成 |
| COMMITMENT-003 | 让用户纠正识别、忽略事项并看到依据 | 纠正/忽略保存后读回且重启恢复；重复旧消息不重新激活已忽略事项；错误写入不显示成功 |
| COMMITMENT-004 | 同版本短演示与中文价值说明 | 展示消息原文、自动更新、变化与出处；演示标明合成来源/真实模型或真实来源；说明少了哪些手动步骤，不虚构节省时间或准确率 |

以上均为待做或待复验，不宣称已完整实现。现有0.5.1验证可复用，但新增语义、取消、乱序、纠正需新证据。App Hub #74 已提交待审核；后续修改另发版本，不改写已冻结v0.5.1。赛事提交和商店审核分别记录。

单来源完整回环先于QQ/Gmail/Outlook全面铺开、Matrix第二来源、提醒、复杂规划及自动回复。官方Mail事件实现和其他参赛者真实宿主验证优先作为参考；不假定商店应用具有系统Mail专有权限。

## 官方依据优先

现有固定运行时尚未升级，真实登录仍待完成。后续在隔离环境评估官方事件队列、账号绑定与撤销机制；新增能力须独立验证。

先检查官方赛事通知、App Design Flow、宿主源码和系统 Mail 示例，再派单。教程日期及宿主提交必须记录；旧教程的“model 尚未合并”不能覆盖已核验源码，也不能据此假定任意宿主均支持模型。

- 赛事要求公开源码、固定版本、许可证、宿主和启动说明、授权及隐私、真实任务证据；包预检、运行验收和评奖独立。
- 官方 script-app flow 的顺序：需求及能力 → doctor → 已存在应用修改 → 原生渲染与交互 → 空/失败/重启 → 修复 → 真实截图及资料 → stamp/check → scan 和独立审查 → 准备交付。不要重复 new 覆盖已有应用。
- 官方 host services 提供 mail.accounts/add_account/folders/sync/list/message；凭证由宿主处理，不能给应用添加密码表单或密钥。
- 新的 OAuth 服务是宿主工作，不属于 OctoScript bundle 内的普通 API 调整。未经官方能力或源码证明，不发明扫码登录接口。

## 当前事实

应用 0.5.0 已实现单一邮箱最近5封的观察、model.complete 语义判断、事项创建/更新/忽略、证据核对、存储读回和去重。合成测试通过不等于真实邮箱和模型质量通过。当前真实邮箱业务回环仍待验收。

用户目标为主动观察授权来源，判断个人事项（例如交稿期限），自动记录变化；不是草稿整理器或关键词规则。初赛以一个来源的最小回环为主，保持纯 OctoScript。

隐私发现：当前锁定宿主 Windows Mail vault 回退 FileVault，源码写入原始 secret 字节，未发现 Windows 加密保护。不得宣称安全加密、不得在此状态要求用户接入私人邮箱凭证。文件夹选择仅限制应用行为，不等于供应商授予的权限只有该文件夹。

## 按依赖执行

| 节点 | 任务 | 验收与停止条件 |
| --- | --- | --- |
| 初赛收尾优先 | 用真实宿主模型分析人工测试内容，先核验原有请求/schema/创建与更新 | 明确标记输入为合成、模型为真实；记录用量和保存读回。不能称真实邮箱回环通过 |
| 首个应用开发任务 | 利用 mail.folders 选择一个来源；mail.sync/list/message 始终显式传该来源；预览后单独启用云分析 | 默认停用；切换来源使迟到结果失效；无选择不读取正文；预览不调用模型；拒绝/停用/重启正确；不得依赖模型先判断隐私再发出正文 |
| 私人邮箱接入前 | 核验官方最新宿主有无现成 OAuth 和 Windows 凭证保护；缺失则独立提出宿主任务 | 查清 token/授权码存储、撤销与缓存范围；无安全存储不接私人凭证。宿主修改与初赛应用分开，不强加自建登录服务为初赛依赖 |
| 一个邮箱可接通后 | 本人授权，测试本人事项、截止变化、他人事项、不同措辞、重复、失败和重启 | 真实读取 → 真实模型 → 正确事项 → 文件读回；仅测试内容公开。无实际结果不冻结为已通过 |
| 10/4 初赛交付 | 锁定实际可运行版本、宿主与依赖；中文首页、启动说明、隐私、截图及同版本演示 | 重新 check/scan，材料与实际功能一致；官方文档当前截止10/4 23:59，最终入口/临时公告须再核验。缺核心回环必须如实列缺口，不保证通过 |
| 初赛冻结后扩展 | QQ、Gmail、Outlook/Hotmail；163/126随后 | 每家独立探针、实现、真实验收；不能把支持列表或按钮当作已支持 |

来源选择先做官方 folder ID，不同时新建 Gmail label API。时间范围需要可信解析且能保证不过界才加入；不能比较任意邮件时间字符串就声称限制成功。只取少量条目不是完整邮箱同步，宿主可能缓存更多邮件，要核验并说明。

## 登录方式与外部条件

- QQ：先取得官方第三方邮件授权文档。QQ 网页扫码登录和普通 QQ OAuth 不等于授予读取邮件；没有可用官方接口证据不实现伪扫码。授权码模式的便利性和存储仍需实测。
- Gmail：若官方宿主已有实现先复用；否则独立宿主任务采用系统浏览器 OAuth、PKCE、state 和本地回调，使用自己的已注册 client。Gmail API gmail.readonly 仍是 restricted scope；测试用户配置、公开验证和云端 AI 数据用途须核查，不以“只读”声称免审核。
- Outlook/Hotmail：同样优先复用宿主；独立实现采用委托 OAuth + Graph Mail.Read，不申请发送/修改权限。应用注册与账号类型支持是实际前置条件。
- 163/126：取得官方授权码/IMAP 文档后再接；不假设通用 OAuth。

## 云分析与开发双环

邮箱授权与发送内容给模型是两个独立决定。显示来源范围、实际正文预览、模型接收方及用途；默认不传附件。连接凭证不进入 bundle、日志、公开仓库。不能保证云分析正文不离开设备，也不能靠撤销邮箱授权撤回已发送正文。

开发仍为 Codex 外环、MiniMax 内环，派单前 mmx quota show，遵守主审锁、持久回执和隔离工作区；独立原生 UI/文件复验后合入。运行时模型与开发代理分开；只使用已确认比赛券，有界请求，余额未知停对应路线。多邮箱、后台进程、Rinx、发送邮件不抢占当前最小回环。
